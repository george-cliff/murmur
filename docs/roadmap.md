# Murmur roadmap

> [!WARNING]
> **Transparency:** this document was generated by AI and will be replaced with a human-written version soon.

This is a rough plan of where Murmur is heading, not a fixed schedule. Phases may change as each stage teaches me more, and a checklist item records direction only; it does not mean the work is implemented. The goal for a first complete version (v1.0) is a second field device built and deployed from the documentation alone.

## Phase 1: Desktop proof of concept

WAV files in, species predictions out, everything stored, without any field hardware.

- [x] Prepare the supported DCASE audio datasets and train the Sparrowhawk bird/not-bird classifier in PyTorch.
- [x] Export Sparrowhawk to ONNX, with a static INT8 quantised variant and a saved threshold.
- [x] Load and resample WAV files and recreate Sparrowhawk's preprocessing in Rust.
- [x] Run Perch species identification only when Sparrowhawk detects a bird call.
- [x] Store detections in SQLite with their model and label records.
- [x] Collect weather, air-quality, and moon-phase data as a separate output.
- [ ] Attach that environmental context to each detection.
- [ ] Process a whole folder of recordings in one run.
- [ ] Replace hard-coded paths and values with a configuration file.
- [ ] Add tests showing that Python and Rust prepare the same audio identically, plus one end-to-end check.
- [ ] Choose a reference Sparrowhawk model and record its evaluation, threshold, and quantised-versus-float comparison.

## Phase 2: Starling on real hardware

Move the pipeline onto one self-contained field device that listens unattended. A Raspberry Pi is the current candidate; the hardware is not confirmed.

- [ ] Cross-compile the Rust pipeline for the target device.
- [ ] Add live microphone input and continuous listening.
- [ ] Run both model stages on the device, keeping detections when it has no connection.
- [ ] Make unattended running reliable: logging to file, automatic restart after a crash, a real-time clock, and database writes that survive power loss.
- [ ] Measure latency, memory, power use, and storage growth on the device.

## Phase 3: Getting detections home

Send small detection messages from the field back to a home base. The radio approach is not yet decided; LoRa and LoRaWAN are among the options being considered.

- [ ] Compare radio options by range, message size, power use, and gateway requirements.
- [ ] Define a compact detection message and a stable identity for each device.
- [ ] Send detections in scheduled batches, with retries, storage while offline, and no duplicates.
- [ ] Prototype the Tern gateway between a field device and the home-server side.

## Phase 4: Nest and Roost

Receive, store, and explore detections at home.

- [ ] Build Nest to receive and store detections, with automatic backups.
- [ ] Make detections easy to query and export as CSV or JSON.
- [ ] Build the Roost dashboard for detections, activity, and device health.
- [ ] Add alerts for notable species and for devices that go silent.
- [ ] Join everything up end to end: field device, radio, home base, and dashboard.

## Phase 5: Field hardening

Make one device dependable outdoors and its results more useful.

- [ ] Weatherproof the hardware and reduce average power draw.
- [ ] Add GPS so a device knows where it is deployed.
- [ ] Focus species identification on UK birds and tune confidence thresholds per species.
- [ ] Optionally keep the short audio clip behind each detection for review.
- [ ] Retrain Sparrowhawk using recordings from the field.
- [ ] Explore contributing records to citizen-science schemes such as the BTO's BirdTrack.

## Phase 6: Ready to scale

- [ ] Replace web-based environmental data with on-device sensors.
- [ ] Support several devices with separate identities.
- [ ] Build and deploy a second Starling using only the documentation (v1.0).

## Ideas requiring further design

- Multi-hop forwarding between field devices.
- Remote configuration and model updates for devices that are often offline.
- Privacy, land access, wildlife disturbance, and retention rules for real deployments.

These are possible later investigations, not current functionality or committed deliverables.
